    Modos de permissão#

    ModoComportamentoPadrão quando
    turbo (--turbo, alias full-auto)com sandbox do sistema: nada que fica no projeto pergunta; só pergunta o realmente necessário (lista abaixo)interativo, sem mode na config, com sandbox que isola (sandbox-exec no macOS, bwrap no Linux)
    autoroda sem perguntar o que não parece perigoso; comando perigoso, rede nova, fora do projeto e arquivo sensível perguntaminterativo sem sandbox; sempre no -p
    plansó investiga e propõe um plano; no fim, um menu pergunta se executa—
    asktudo que não é só leitura pergunta (o modo certo pra repositório desconhecido)pasta que você não confiou
    smartedição no projeto e comando só-leitura rodam direto; o resto passa por um modelo rápido, que responde SAFE ou ASK; pacote, git que altera, rm/sudo, .env/chaves e a config do jazz sempre perguntam— (/mode smart, --smart)
    yolodispensa confirmações rotineiras; guardas de dados sensíveis continuam ativas; use em container ou VM— (--yolo)

    O modo aparece na tela de boas-vindas (com uma linha explicando o que ele faz, na primeira vez) e no rodapé da caixa de entrada. /mode <modo> troca e grava na config; Shift+Tab ou Ctrl+T alterna só nesta sessão: turbo → auto → plan → ask → turbo (sem sandbox o turbo sai do ciclo, porque seria igual ao auto; smart fica no /mode smart). Flags --ask, --smart, --turbo, --yolo; config "mode": "auto" (ou qualquer outro) fixa o modo e vence o padrão. Numa pasta que você ainda não confiou, a sessão roda em ask; com --turbo explícito o modo fica, mas bash que muda algo ainda pergunta até você confiar (no -p: jazz trust --yes antes).

    Quem já tinha config.json de uma versão anterior: o jazz gravava "mode": "auto" ao salvar qualquer coisa, e isso continua valendo como escolha sua. Para o padrão novo (turbo com sandbox), apague a linha mode ou use /mode turbo.

    Confirmações como no Claude Code. Toda pergunta é um menu numa caixa: a pergunta de permissão mostra o comando exato (ou o diff da edição), o motivo de risco em vermelho por inteiro, uma linha por problema, e as opções em lista vertical:

    ╭─ Bash ──────────────────────────────────────────────╮
│ git push --force origin feature/x                   │
│                                                     │
│ ⚠ git push forçado                                  │
│                                                     │
│ Rodar este comando?                                 │
│ ▸ 1. Sim                                            │
│   2. Sim, e não perguntar de novo neste projeto …   │
│   3. Não, e me diga o que fazer                     │
╰─────────────────────────────────────────────────────╯

    ↑↓ (ou j/k) e Enter escolhem; o número escolhe direto; atalhos de uma tecla: s sim, a sempre, n/esc não, e não + instrução, v mostra o comando, o diff e o motivo inteiros. Enter é sempre a opção destacada (Sim ao abrir). Tecla nos primeiros 250 ms, ou enquanto você ainda está digitando (sem pausa de 600 ms), não responde. O que você digitou enquanto o agente trabalhava fica na fila, aparece acima da caixa (↳ na fila: …) e volta pra caixa de entrada; nunca muda o significado das teclas. Nunca é preciso digitar sim.

    O que a opção 2 lembra, como no Claude Code (always_scope, padrão auto):

    Pergunta"Sim, e não perguntar de novo"Onde fica
    edição/escrita (modo ask)nesta sessão, para Edit(<pasta>/**)memória (some ao sair)
    comando, domínio, ferramenta MCP, scriptneste projeto, para a regra derivada (Bash(npm test:*), WebFetch(domain:x)).jazz/settings.json (/permissions)
    motivo de risco (host novo, pasta fora do projeto, git destrutivo, curl|sh de um host, pacote)neste projeto, para aquele par (classe, alvo).jazz/approvals.json (/approvals, /approvals clear)

    always_scope: "session" faz tudo durar só a sessão; "project" grava também as edições. Ler segredo, comando catastrófico, regra ask, hook e injeção suspeita perguntam sempre.

    Pasta nova. Na primeira vez numa pasta aparece um menu: 1. Sim, confiar nesta pasta (Enter; lembrado nas próximas vezes), 2. Só nesta sessão, 3. Não, modo ask (Esc). Pasta sem configuração própria recebe a pergunta curta ("Primeira vez nesta pasta. Confiar?"); com AGENTS.md, .mcp.json, hooks, scripts ou steering, a caixa lista tudo que vai ser carregado (v mostra a lista inteira). trust_default: "always" na config confia sem perguntar em pasta sem configuração própria (a que traz configuração continua perguntando).

    Outras perguntas, mesmo menu: executar o plano (fim do plan), jobs em segundo plano ao sair ou no /clear, /forget, o atalho determinístico (⚡ atalho), ask_user e /rewind (lista com filtro: digite pra filtrar, ↑↓/PgUp/PgDn, Enter abre, Esc cancela; a lista é apagada depois) e, fora da sessão, jazz trust, jazz worktree merge e jazz improve.

    Turbo em 5 linhas. (1) Só existe de verdade com o sandbox do sistema (sandbox-exec no macOS, bwrap no Linux); sem ele vira auto e avisa uma vez. (2) Roda sem perguntar teste, build, formatação, git add/commit, edição, leitura, script e pacote limpo, numa pasta que você confiou. (3) Pergunta só: escrita/remoção fora do projeto; envio de dados a host novo (a primeira vez); leitura de segredo; git destrutivo (push --force, branch -D, filter-repo, clean -f, reset --hard em branch compartilhada); pacote que o guardrail de supply chain marca; comando catastrófico (rm -rf da home, disco, chmod -R 777 /, sudo, curl|sh); regra ask, hook, injeção suspeita no turno; e, em pasta não confiada, bash que muda algo. (4) git checkout -- ./restore ./reset --hard em branch local não pergunta porque o checkpoint shadow-git desfaz (/undo). (5) Decide sem chamar modelo; cada aprovação automática vai pro log de auditoria com a regra que liberou.

    O custo de segurança, dito sem rodeio: no turbo o que protege você dentro do projeto é o sandbox, não uma pergunta. Um comando ruim pode apagar ou estragar arquivos do projeto (o checkpoint cobre arquivos versionáveis de até 1 MB, não .gitignored) e pode mandar o conteúdo do projeto pra um host que você já aprovou. O sandbox impede ler sua home e segredos e escrever fora do projeto, mas a rede continua aberta (use --sandbox strict pra cortar). Repositório desconhecido: ask.

    Permission modes#

    ModeBehaviourDefault when
    turbo (--turbo, alias full-auto)with an OS sandbox: nothing that stays inside the project asks; it only asks when really necessary (list below)interactive, no mode in config, and a sandbox that isolates (sandbox-exec on macOS, bwrap on Linux)
    autoruns whatever does not look dangerous; dangerous commands, new hosts, outside the project and sensitive files askinteractive without a sandbox; always with -p
    planinvestigates and proposes a plan; a menu then asks whether to run it—
    askeverything that is not read-only asks (the right mode for an unknown repository)a folder you did not trust
    smartproject edits and read-only commands run; the rest goes to a fast model that answers SAFE or ASK; packages, mutating git, rm/sudo, .env/keys and jazz's own config always ask— (/mode smart)
    yolonothing asks; only inside a container or VM— (--yolo)

    The mode shows on the welcome screen (explained in one line the first time) and in the input box footer. /mode <mode> switches and saves; Shift+Tab or Ctrl+T cycles for this session only: turbo → auto → plan → ask (turbo leaves the cycle without a sandbox; smart stays on /mode smart). Flags: --ask, --smart, --turbo, --yolo; a config "mode" wins over the default (older versions saved "mode": "auto" on any save: delete it to get the new default). In a folder you have not trusted yet (jazz trust), the session runs in ask; with an explicit --turbo the mode stays, but bash that changes something still asks until you trust the folder (with -p: jazz trust --yes first).

    Confirmations like Claude Code: every question is a boxed menu: the exact command or diff, the whole risk reason in red (one row per problem), and the options as a vertical list (1 Sim, 2 Sim, e não perguntar de novo…, 3 Não, e me diga o que fazer). ↑↓/j/k + Enter, the digit, or one key: s yes, a always, n/esc no, e no + instruction, v the whole command, diff and reason. Enter is the highlighted option. Text typed while the agent works stays queued and is shown above the box. "Always" without a risk reason lasts this session for edits and is a project rule for commands and domains (always_scope: auto|session|project). No typing sim. "Always" on a prompt with a risk reason (new host, folder outside the project, destructive git, curl|sh from a host) is kept in .jazz/approvals.json and never asked again in that project; /approvals lists, /approvals clear wipes. Secret reads and catastrophic commands ask every time.

    Turbo in 5 lines. (1) It only exists with an OS sandbox (sandbox-exec on macOS, bwrap on Linux); without one it is auto and says so once. (2) Tests, builds, formatting, git add/commit, edits, reads, scripts and clean package installs run without asking in a folder you trusted. (3) It asks only for: writes/deletes outside the project; sending data to a new host (first time); reading secrets; destructive git (push --force, branch -D, filter-repo, clean -f, reset --hard on a shared branch); packages the supply-chain guard flags; catastrophic commands (rm -rf of home, disk ops, chmod -R 777 /, sudo, curl|sh); ask rules, hooks, a suspected injection in the turn; and, in a folder not trusted yet, bash that changes something. (4) git checkout -- ./restore ./reset --hard on a local branch do not ask because the shadow-git checkpoint undoes them (/undo). (5) It decides without calling a model; every auto-approval goes to the audit log with the rule that allowed it.

    The security trade-off, plainly: in turbo what protects you inside the project is the sandbox, not a prompt. A bad command can delete or damage project files (the checkpoint covers versionable files up to 1 MB, not .gitignored ones) and can send project content to a host you already approved. The sandbox stops reads of your home and secrets and writes outside the project, but the network stays open (use --sandbox strict to cut it). Unknown repository: ask.
